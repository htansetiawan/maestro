What exactly runs, and how it was checked
GraphOne decoding step: next event in, logits and the extended key-value cache out (6 layers, 8 heads, relative attention over a 1,024-position table, 2,048-event context). The relative term for one query is its dot product with every relative embedding, gathered by each key's distance.
WeightsStored as 16-bit floats and cast to 32-bit inside the graph (the runtime folds the casts at load), so arithmetic is 32-bit. File hash @@MODEL_SHA@@…, from checkpoint @@CKPT_SHA@@….
Check against PyTorchOver @@CHECK_POSITIONS@@ positions of the first frozen opening: largest logit difference @@CHECK_LOGIT@@, identical most-likely event at @@CHECK_AGREE@@% of positions, mean NLL @@CHECK_NLL_ONNX@@ (graph) against @@CHECK_NLL_TORCH@@ (PyTorch).
SamplingReserved ids masked; temperature, then nucleus filtering with the same rule as the pool sampler; a seeded 32-bit generator, so a seed replays. The pool itself was sampled on the GPU with seed @@SEED@@; browser samples will differ from it by construction (different generator).
SpeedMeasured in this browser once the model runs.
Runtimeonnxruntime-web 1.30.0, WebAssembly backend, single thread (this site does not set cross-origin isolation headers). Prompt set v1 hash @@PROMPTS_SHA@@….

Pianist or model?

Each round takes one of the @@N_PROMPTS@@ openings. Both clips begin with the same opening, played by the pianist. After it, one clip continues with the pianist's own next 1,024 events from the MAESTRO recording; the other continues with the model's first sample for that opening (candidate 0 at seed @@SEED@@, never chosen by ear). Both are rendered by the same piano. Pick the pianist.
